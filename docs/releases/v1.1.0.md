DiskScope 1.1.0: about 3× faster scans, roughly a third of the memory, and leaner output for agents.

Download **DiskScope-1.1.0-win-x64.zip**, extract it over your previous folder, and restart your MCP client. **Existing snapshots must be rebuilt once with `disk_scan`**, because the index format changed.

**Speed and memory** (measured on one local Windows 11 NTFS system drive; see `docs/PERFORMANCE.md`):

| | 1.0.1 | 1.1.0 |
| --- | --- | --- |
| System-drive scan | 17.5 s | ~5.5–6.5 s |
| Cold load + first browse | 4.9 s | ~0.7 s |
| Resident index memory | ~1.06 GB | ~360–380 MB |
| Snapshot on disk | — | ~96 MB (ZLib) |

- **Faster scans:** the MFT `$BITMAP` is used to skip unused record ranges, with two overlapping readers and parallel parsing. Full-read fallback is kept.
- **Compact index:** packed arrays, a deduplicated name pool and CSR children replace per-record objects. Snapshots are saved atomically in a new v3 format with ZLib Fastest compression.
- **Cleanup keeps the index current:** after an audited cleanup, a loaded index removes only the deleted names and saves itself, so you don't need a full rescan. A stale index or hard-link drift still asks for a rescan. Deletion safety checks are unchanged.

**Agent experience**

- **Compact output by default:** browse, largest and detail rows are about 55% smaller and include each item's share of the parent. Use `verbose: true` (or `--verbose`) for the 1.0.x field set.
- **`disk_job_status` can wait:** `wait_seconds` (0–30) holds the call until the job finishes, so you don't need to poll. When a `progressToken` is supplied, MCP progress notifications are sent.
- **New `disk_types` tool / `types` command:** shows space by file extension and category for any subtree, counting hard links correctly. There are now 13 tools, 9 of them in analysis-only mode.

Validated with 127 core checks and 44 packaged MCP/CLI checks, plus live NTFS scans with record counts matching 1.0.1.

**Cleanup still permanently deletes files and bypasses the Recycle Bin.** The executable remains unsigned; verify it with the SHA-256 checksum.
